Nize Logistics — Platform Flow

End-to-end: account creation → rider operations → order lifecycle → tracking → settlement. Every endpoint listed.

Actors

  • Super Admin — invites admins, edits fare metrics, full audit
  • Admin — invites riders, assigns orders, watches the fleet
  • Rider — goes online, accepts/declines, executes the delivery
  • Customer — books an order and tracks it, no account needed

Access rules

  • Public site has no sign-in link — staff arrive by admin invite only
  • /login still works for anyone who holds a URL
  • /signup/:token is the only way to create a staff account, and the token is single-use
  • New riders are gated by must_change_password until they set their own password

3 · Order lifecycle — the full state machine

pending→ assigned→ accepted→ picked_up→ in_transit→ delivered

Every legal transition (enforced server-side)

  • pending → assigned · admin assigns a rider
  • pending → cancelled · customer or admin cancels
  • assigned → accepted · rider accepts
  • assigned → pending · rider declines (unassigns)
  • accepted → picked_up · rider reaches the sender
  • accepted → pending · rider backs out
  • picked_up → in_transit · rider departs
  • picked_up → delivered · same-location shortcut
  • in_transit → delivered · rider completes
  • delivered / cancelled — terminal, nothing leaves them

Rejection handling

  • Decline only legal from assigned — anything else returns 409
  • Declining returns the order to pending with declinedCount + 1
  • declinedCount feeds the admin alert threshold
  • Every decline writes an audit entry and emits admin:order-update
  • No penalty, no auto-reassign — an admin must reassign by hand

4 · Immediate vs scheduled

Immediate

  • Customer books → pending
  • Admin assigns → assigned
  • Rider accepts and runs it now
  • Route drawn from decoded Plus Codes, priced live by OSRM

Scheduled

  • Booking carries a scheduledFor timestamp
  • Sits in pending until dispatch
  • Admin assigns at the chosen time
  • Same rider flow from assigned onward

7 · Honest gaps

Not built — no returns, no disputes. There is no returns or disputes table, endpoint, or screen anywhere in the codebase. A customer who receives a damaged or wrong parcel has no channel to report it. If you want it, it needs: a table, a POST /api/disputes (customer) and an admin review flow.
Not built — no rider payout. Earnings accumulate per rider but nothing settles them. No payout table, no admin approval, no transfer integration.
Not built — no multi-tenancy. Every table lacks organization_id. One company per deployment works; two companies on one database would share data.
Working. Order lifecycle and rejection handling are enforced by a server-side transition table — a rider cannot deliver an order they never picked up, and an illegal jump returns 409.
